NAME — tiny · credential-less Claude Code & Codex sessions on your own Kubernetes

HOLDS NO KEYS

No keys. No open ports. Your cluster.

An agent that reads issues and pulls dependencies will eventually be told what to do by someone who is not you. On your laptop it does that as you, with your keys and your network. tiny runs the real Claude Code and Codex CLIs as pods on your own Kubernetes instead, holding nothing worth stealing: no git credentials by default, no cloud credentials, nothing listening on the pod, egress denied by default. Work leaves as a signed-off bundle a courier pushes. When it asks to do something risky, your answer runs as you — not as the agent. And the session keeps working after you close the lid.

Pick a move a prompt-injected agent might try:
You. Your laptop or CI runs tiny, which talks to the Kubernetes API with your own kubeconfig. Attaching is an exec into tmux under your RBAC. When a session asks a question, answering runs the action in your client with your credentials, so the audit log names you, not a service account.
Init container. Copies Claude Code, Codex, a static tmux and the entrypoint into a shared /tiny volume, then exits. The session runs from /tiny, which is why --image can be golang:1.26 or your own dev image. There’s no special image to maintain and nothing baked in.
The agent. The real, unmodified Claude Code or Codex CLI in tmux, as a non-root user, under the restricted profile: the runtime’s seccomp filter, every Linux capability dropped, no privilege escalation. It runs with permissions bypassed on purpose, so nothing intercepts its tool calls. The boundary is everything drawn around it.
MCP sidecar. tiny’s own tools (ask a human, list or spawn sessions, publish a port) on 127.0.0.1:8080, reachable only from inside the pod. It runs as the session’s service account, which may create questions, read sessions and pods, and update its own status. Nothing else: no delete, no exec, no secrets, no ConfigMaps.
Workspace volume. A persistent volume at /workspace holding the repo, the transcript and outbox/. The pod is disposable and the volume isn’t, so a replaced pod resumes the conversation. Finished work is written as git bundle create outbox/<branch>.bundle main..<branch>: a file, not a push.
The one secret. tiny-agent-env holds the model credential, a Claude token or an API key, because the real vendor CLI can’t run without it. No git token, no cloud keys, no SSH key, unless you opt into a deploy key in tiny setup, which then does live in the pod.
Egress policy. One NetworkPolicy on every session pod, on by default. Allowed out: DNS, this namespace, the Kubernetes API, and ports 80 and 443 to the internet minus private address space, so 169.254.169.254 and your internal network are unreachable. Every other port is closed. It only bites if your CNI enforces NetworkPolicy, and the fleet screen tells you whether it does.
Egress proxy, optional. Switch on the hostname allow-list and the internet rule disappears. Every connection goes through a CONNECT proxy that checks the hostname and tunnels TLS without breaking it. It’s also the session’s only DNS resolver: cluster names are answered, everything else is refused. Refusals show up in tiny egress denied.
Kubernetes API. Anything the agent might want to change goes through here, and RBAC answers. With the session’s own token, deleting itself, rewriting its task, editing the allow-list, reading secrets and approving its own question all come back 403. We tested exactly that from inside a live pod.
Courier. A GitHub Actions job on the in-cluster runner, holding the job’s short-lived GITHUB_TOKEN. It reads each workspace’s outbox through the exec API, argv only, with bundle names checked against a strict pattern. Then it rebases, pushes, opens the pull request, and only after that marks the bundle done. The token never enters the session pod.
GitHub. Receives branches and pull requests from the courier, never from the agent. When the agent needs a decision, the question appears as a comment on the issue with the exact tiny answer command, which you run with your own credentials.
The internet. The agent has to reach its model API. With only the egress policy, any host on 443 is reachable. With the allow-list on, only the hosts you listed are.

OPTIONSthe machinery under both
--the-real-thing
Attaching puts you in the actual Claude Code CLI over a TTY: hotkeys, plan mode, skills, your .mcp.json. tiny does not wrap or proxy the agent, so new agent features work without us doing anything.
--survives-anything
The workspace is a persistent volume; the pod is disposable. Kubernetes replaces dead pods on its own, and the replacement resumes the transcript.
--image any:tag
golang:1.26, buildah, your own dev image: an init container injects the agent into whatever you name. You do not maintain a special image.
--humans-hold-the-gate
Dangerous moves park as Question objects until you answer. Your y approves and performs the action with your credentials, so the audit log names you rather than a service account.
--no-credentials
Pods store no deploy keys or tokens. Work leaves through the outbox, so a compromised agent cannot push or call GitHub. On a laptop, a bypass-mode agent has your SSH keys and browser sessions; here it has a workspace and a model token.
--no-control-plane
There is no operator or manager pod; the CLI and Kubernetes do the work. The namespace holds only the sessions you run and the add-ons you switched on.
--tmux-native
Every session lives in tmux. Attaching is a real tmux attach, with panes and scrollback, and detaching does not stop the agent.
--resources cpu,mem
Per-session requests and limits from the session spec. The fleet screen shows each session's own CPU and memory readings.
--drop-a-file
Drag a file onto a session’s row in the fleet screen and it lands in that workspace under /workspace/uploads/.
--agent claude|codex
Claude Code by default; --agent codex runs OpenAI’s Codex. The fleet screen, the gate and resume behave the same for both.
--model your-pick
Pin the model per session (claude --model / codex -m underneath). Also a field on the options form.
--broadcast
One message into every unfinished session's inbox: [b] on the fleet screen, or tiny broadcast from cron and CI.

[✓] registry-cacheZOT

Pull-through image cache in your namespace. golang:1.26 downloads once instead of once per session, which also keeps you under docker.io rate limits. An optional DaemonSet installs its CA on the nodes.

[✓] artifact-storeMINIO

S3-compatible store next to the sessions, for things too big for git: builds, screenshots, datasets.

[✓] github-runnerACTIONS

In-cluster Actions runner, so delivery jobs can reach the sessions. A labeled issue lands in an inbox in about five seconds.

[✓] web-pageREAD-ONLY

The fleet as a page, plus each session’s blast radius: files changed, lines, branch, and the files two sessions are both editing. Port-forward to reach it; it can only read.

[✓] egress-policyNETWORK

Default-deny networking for sessions: this namespace and http/https out, nothing else. Closes the cloud metadata endpoint and every other port. It does not stop exfiltration over 443 — and it only bites if your CNI enforces NetworkPolicy, which the screen tells you.

[✓] hostname allow-listEGRESS PROXY

All outbound traffic through a CONNECT proxy that filters by name, not address — the thing a NetworkPolicy cannot do. TLS is never terminated; the hostname is read before the tunnel opens. Closes the DNS channel too. Refusals name the host and get logged.

FOR YOUR TEAMthe loop: issue in · PR out

Label an issue. Harvest a pull request.

1

Sow

File a GitHub issue and add the tiny label. That is the whole ceremony. Anyone on the team can do it from the GitHub UI.

2

Deliver

An Actions job on the in-cluster runner pipes the issue into the root session's inbox. It usually takes about five seconds.

3

Grow

The root session plans, spawns specialists in the right toolchains, and raises a ✳ when a decision needs a human. Overnight is fine; we test session recovery by killing pods mid-task.

4

Harvest

Agents hold no credentials. Finished branches leave as git bundles through the outbox, and a short-lived courier token opens the pull request and comments on your issue.

THE ENTIRE INTEGRATION.github/workflows/tiny.yml
on:
issues: { types: [labeled] }
jobs:
deliver:
if: github.event.label.name == 'tiny'
runs-on: [self-hosted, tiny]
steps:
- run: |
printf 'issue #%s: %s\n\n%s' "$N" "$TITLE" "$BODY" \
| tiny deliver root --ensure --repo "https://github.com/$REPO.git"
the task hand-off is a prompt piped into tiny deliver · full workflow in the docs
